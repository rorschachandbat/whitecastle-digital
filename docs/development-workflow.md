# 开发与版本管理约定

## 规则依据

规则文档是行为需求的基准。实现、测试或参考项目与规则基准不一致时，先定位规则来源；不能因为已有代码或测试通过就认定它符合桌游规则。

修改游戏行为时，应在变更记录中写出对应规则章节或规则编号，并区分：

1. 规则要求的行为；
2. 本次实现覆盖的范围；
3. 尚未覆盖或需要确认的边界。

待确认规则不得悄悄用猜测代替。可以临时限制功能范围，但必须让使用者知道限制。

## 每批改动与提交

每个提交应对应一批相关且可审查的改动，例如“修正资源终局计分并补齐边界案例”。避免把多个无关功能混为一个提交。

每批改动完成时：

1. 检查本批差异，排除缓存、账号信息、私人数据、临时下载和无关文件。
2. 更新根目录 `CHANGELOG.md`。
3. 如果修改主要模块，更新该模块旁的 `CHANGELOG.md`。
4. 完成当前授权范围内的检查，并记录实际结果。
5. 提交到 Git；推送成功后记录可核验的提交编号。若推送失败，明确保留的本地提交与失败原因。

用户已授权本项目按进展提交和推送，不需要为每个普通提交重复申请许可。重写远程历史、强制推送、删除远程分支等动作不属于普通进展上传。

提交信息应描述结果，例如：

```text
docs: 建立规则基准与开发约定
feat: 增加桥上取骰与放置流程
fix: 保留训练场武士跨轮状态
```

不要求每保存一次文件都产生提交。提交单位是完整的相关改动批次，确保每次上传都可说明、可审查。

## CHANGELOG 层级

根目录 `CHANGELOG.md` 面向项目使用者和验收人员，概括功能、行为修正、兼容性影响和验证状态。

主要模块的 `CHANGELOG.md` 放在该模块目录中，与代码相邻，不需要在每个源文件内重复完整历史。模块边界以实际目录结构为准，例如：

```text
CHANGELOG.md
src/
  game/
    CHANGELOG.md
  ui/
    CHANGELOG.md
```

上例为结构示例，不要求为了变更记录创建空模块。引擎、网页界面、外部数据适配器、AI 搜索等模块建立时，再为其创建记录。

每个模块记录应包含：

- 日期及本次目的；
- 具体行为变化与对应规则；
- 主要文件或接口；
- 影响范围与迁移事项；
- 实际检查结果；
- 推荐人工验证步骤和已知限制。

根记录和模块记录应互相补充，不必逐字重复。不要在待提交内容中预填不存在的 Git 提交号。

## CHANGELOG 条目模板

```markdown
### YYYY-MM-DD — 本批变更名称

#### 变化与原因

- 描述触发条件、原行为和新行为。
- 对应规则：规则编号或章节。

#### 影响

- 受影响模块、接口、存档或页面。
- 没有迁移要求时也应基于实际判断说明。

#### 验证

- 实际执行：检查名称及结果。
- 未执行：检查名称及原因。

#### 推荐验证

- 给出可重复的输入、操作和预期结果。

#### 已知限制

- 明确本次尚未实现或未能确认的行为。
```

## 编译与检查

除非用户在当前请求中明确要求编译，否则不得运行编译或构建命令。

测试、启动和预览命令也可能隐式触发编译。在执行前应查看脚本内容，不能通过 `test`、`dev`、`preview` 等名称规避这条约定。

可以在授权范围内执行不触发编译的检查，例如 Git 差异检查、JSON 格式检查、链接目标检查、源码静态审查，以及可直接运行且不会编译项目的检查。

检查结果必须如实记录：

- 只读源码不能写成“运行验证通过”；
- 未启动网页不能写成“浏览器验证通过”；
- 未运行测试不能写成“测试全部通过”；
- 未成功推送不能写成“已上传 GitHub”。

修改后应说明推荐的编译和人工验证步骤，由用户选择何时执行。

## 注释、文案与脚本

- 新增或修改代码注释时使用中文，除非用户明确要求其他语言。
- 玩家可见文本必须使用 StringTable，通过稳定的键引用；诊断日志和开发文档应与玩家文案区分。
- 脚本从自身位置、调用参数或工作副本元数据推导目录，不硬编码分支名或本机绝对路径。
- 配套脚本与启动器相对定位，说明需要一起复制的文件和目录结构。
- 更新公用脚本后，应检查或推演它在另一分支同布局工作副本中的执行方式，记录剩余环境依赖。

## 分 agent 协作

为各 agent 分配清晰的文件或模块范围。跨模块接口变更先通知协调 agent，避免同一文件被并发覆盖。

协调 agent 汇总差异、核对文档与实现的一致性，再统一提交和推送。其他 agent 不擅自重置工作区或覆盖未确认来源的改动。
