# 实现计划与验收边界

## 当前交付

当前已提供规则基准、boardgame.io 工作台骨架、两人可编辑数据目录、配置编辑器和纯规则引擎第一批核心。网页 Client 仍为骨架，完整规则引擎及合法动作枚举尚未完成；本批范围见 [engine-core.md](engine-core.md)。

本计划描述后续工作，不代表完整规则引擎、网页对局、自动部署或 AI 已经完成。每个阶段完成时更新根目录及相关模块的 CHANGELOG，报告实际检查结果后提交、推送。

用户指定的实现顺序与验收门槛：纯规则引擎 → 合法动作模型 → 网页棋盘（包含 boardgame.io 适配）→ Yucata 复盘适配 → AI 搜索。每一步停下来让用户验收；数据核验贯穿各阶段，不能以缺失资料为由猜测开局。

## 总体结构

建议将规则模型与 boardgame.io 适配层分离：

```text
经核验的组件数据 + docs/RULES.md
                  ↓
纯规则引擎：合法行动、状态转移、计分
                  ↓
boardgame.io：回合会话、多人同步、玩家视角
                  ↓
网页界面：棋盘、动作选择、StringTable

Yucata 公开数据 → 只读适配器 → 标准局面/动作记录
                                   ↓
                          复盘与差分验证

纯规则引擎 + 可恢复状态 → 搜索/自我对弈 → 分析结果
```

规则的最终依据始终是 `docs/RULES.md`。外部实现与线上数据用于参考和交叉验证，不能替代规则校准。

## 前置与持续工作：规则与组件数据核对

目标：建立可追溯的数据字典，不以猜测数值补齐规则。

工作：

- 按规则编号建立组件及机制核对表。
- 核对个人面板各行、移走人员后揭开的收益、时间轨、各类卡牌和板块的数量与内容。
- 为数据建立稳定 ID、来源、适用人数和版本字段。
- 将尚缺图像或明确数值的条目保留为待确认，不开放依赖这些条目的完整模式。
- 建立 Yucata 数字 ID 与本项目 ID 的显式映射；没有证据的映射不能通过名称相似推定。
- 记录第三方资料的授权范围，不将未确认许可的源代码直接迁入实现。

验收：

- 每份规则数据都能对应来源和规则条款。
- 两人基础版所需数据的已确认项与缺失项清楚列出。
- JSON 等数据格式完成不触发编译的结构检查。
- 测试夹具只使用已确认配置，临时数据明确标注。

## 阶段一：纯规则引擎

目标：在没有网页和网络的情况下，表达准确且可复现的两人基础版。

建议接口：

```text
createGame(seed, setup)
getLegalActions(state, actor)
step(state, action)
score(state)
exportFullState(state)
importFullState(data)
getObservation(state, player)
```

工作：

- 区分全局轮、玩家回合和回合内子决策。
- 建模取骰、支付点数差、灯笼奖励、放置区行动及可选执行顺序。
- 使用明确的待处理决策队列或栈，处理资源选择、费用、人员移动和连锁行动。
- 正确处理当前个人行动牌与灯笼区的替换关系。
- 正确处理轮末行动顺序、花园激活、武士保留、最终计分和同分判定。
- 让合法动作生成与动作执行共用同一套校验约束。
- 以可控制随机源处理掷骰、洗牌等随机事件。

验收：

- 任意 `getLegalActions` 输出的动作，在同一个状态上均能被 `step` 接受。
- 非法动作不会部分修改状态。
- 同一初始状态、随机源和动作序列产生同一结果。
- 不存在无规则依据的免费跳过或资源增益。
- 所有行为边界对应规则编号；未覆盖机制准确记录。

## 阶段二：合法动作模型

目标：完整引擎验收后，建立网页、复盘与 AI 共用的合法动作入口。

工作与验收：

- 实现 `getLegalActions(state, actor)`，与 `applyAction` 共用校验。
- 覆盖回合内选择、费用、目标、每回合使用记录与连锁动作。
- 每个生成的动作都能在原状态执行；非法动作不修改状态。
- 配置变化需新建实验，不混用旧局面；不同种子与配置可重复验证。
- 完成后停下来验收，再进入网页。

## 阶段三：网页棋盘中的 boardgame.io 适配

目标：使用框架管理对局，而不重复维护第二套规则。

工作：

- 将纯引擎动作封装成 boardgame.io 的 moves。
- 确定 `G`、`ctx`、phases、turn 与 pending decisions 的职责边界。
- 让框架回合推进与游戏子决策协调，避免每次子动作都结束玩家回合。
- 通过玩家视角过滤提供每名玩家可见状态。
- 统一无效动作、重连、结束对局和日志展示的行为。
- 先提供本地双人验证入口，再评估服务器多人会话。

验收：

- 同一局面通过纯引擎或框架 move 执行时，规则结果一致。
- 客户端不能依靠按钮状态绕过服务端或引擎校验。
- 框架状态和完整存档格式各自职责明确。
- 网络同步不改变规则执行次序。

## 阶段三：网页棋盘与客户端

目标：让玩家能看懂局面、完成行动并理解限制。

工作：

- 绘制桥、城堡、花园、训练场、水井、城外和个人面板。
- 按当前合法动作显示可选目标，分清常规行动和连锁子选择。
- 提供费用、收益、待处理决策、行动顺序和计分明细。
- 所有玩家文案由 StringTable 提供，通过稳定的键读取。
- 界面布局适应常见桌面尺寸；移动设备支持单独记录验收范围。
- 明确标识未实现模式或待核验数据，不将它们显示成可用功能。

验收：

- 每个界面操作都有明确的规则动作映射。
- 资源支付前后、灯笼触发和换牌结果能被玩家核对。
- 错误提示和操作说明不包含内部实现细节。
- 在用户授权启动或编译后，再进行真实浏览器交互验证。

## 阶段四：Yucata 只读适配与复盘

目标：导入已观察的公开局面和动作，辅助验证与复盘。

工作：

- 兼容动作日志中的 `P/E/A` 与 `ActionParams/ActionEffects/Automatic` 字段。
- 区分玩家选择、自动动作、已确认动作、重做栈和完整回合。
- 保留未识别字段和原始编号，不猜测未确认语义。
- 将外部状态映射到本项目模型，记录无法恢复的内部状态。
- 对齐资源、棋子位置、当前个人行动牌和计分，输出可定位的差异。
- 不把效果日志误当成完整状态补丁，也不依赖线上服务器执行 AI 的假想分支。
- 原始对局中的个人信息在提交前做最小化处理。

验收：

- 已保存样本能稳定解析，字段差异有覆盖。
- 每个映射关系都有依据。
- 可复盘部分和缺失历史状态的部分明确分开。
- 对局导入不会向原房间提交动作。

## 阶段五：AI 搜索与分析

目标：先得到可解释、可比较的候选路线，再考虑训练神经网络。

工作：

- 建立随机与简单启发式基准。
- 加入 MCTS 或其他适合多阶段动作与随机事件的搜索。
- 支持状态克隆或执行/撤销，避免每个节点重新创建整场对局。
- 将自动环境转移和玩家决策区分，合法动作掩码来自规则引擎。
- 记录搜索预算、随机种子、候选行动、估值与结果稳定性。
- 在规则通过差分验证后，再评估自我对弈、策略/价值网络和训练成本。

验收：

- AI 不会选择动作生成器之外的非法动作。
- 相同配置可复现搜索实验。
- 报告胜率、分差等指标时，同时记录对手、样本数与预算。
- 未完成训练和基准对比前，不宣称达到最优或专业强度。

## FullState 与 Observation 分离

`FullState` 是引擎内部或受控模拟使用的完整状态，包括隐藏牌堆、随机过程所需状态、待处理决策和完整存档信息。

`Observation` 是某名玩家或 AI 决策时有权知道的视角。它可以包含公开棋盘、该玩家可见信息和合法动作，但不能暴露尚未公开的牌堆顺序或随机结果。

设计要求：

- 保存和恢复完整模拟使用 FullState，不把公开快照误作完整存档。
- 网页与 AI 默认消费 Observation。
- boardgame.io 的玩家视角过滤和规则引擎观察接口保持一致。
- 对未来隐藏信息和骰子结果做搜索时，基于允许的信息采样，不把真实未来数据泄漏给策略。
- 训练数据中的标签和奖励可以在对局结束后生成，但决策输入仍应保持当时的信息边界。

## 验证计划

验证分为规则校准、状态不变量、样本差分和界面操作，不以代码覆盖率代替规则正确性。

优先覆盖：

- 资源 0、3、6、7 的终局计分；
- 金币与印章合并计分；
- 左端取骰的灯笼结算时机；
- 旧个人牌进入灯笼区，新牌替换当前牌；
- 牌堆耗尽仍可执行浅色行动；
- 武士和园丁跨轮保留；
- 轮末花园的玩家顺序、行动顺序与连锁；
- 行动费用、资源上限和非法动作原子性；
- 合法动作掩码与实际执行一致；
- State/Observation 不泄漏未来或隐藏信息。

本计划本身不授权运行编译。每个阶段先完成不触发编译的检查；需要编译、构建、启动或会隐式编译的测试时，按用户当前请求的明确授权执行。GitHub 普通推送不得自动触发构建。
